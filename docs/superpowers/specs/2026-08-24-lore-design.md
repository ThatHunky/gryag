# Лор чату — Design Spec

**Date:** 2026-08-24
**Status:** approved, not yet implemented
**Builds on:** `2026-08-19-gryag-v3-design.md` and `2026-08-19-superapp-design.md`, which
describe the running bot

The chat gets an autogenerated lore document: a living page of plain-language chronicle,
in the chat's own register, rewritten every couple of days from what actually happened.
`/lore` sends it as a Markdown file. Nobody but the schedule and the admin can make the
bot write it.

This is the second thing in the project that spends tokens thinking *about* the chat
rather than speaking in it. The V3 governing rule is unaffected:

> **The LLM is called only when the bot speaks.** The decision to speak is plain code.

Reading the lore never calls the model. Writing it happens on a timer, off the message
path, exactly like the digest.

Four pieces of work, in order:

1. **Capture** — reactions and service events reach the database for the first time.
2. **Backfill** — the 2026-08-24 Telegram export is imported, recovering the week before
   the bot existed.
3. **Generator** — `gryag/lore.py`, a two-stage job that rewrites the document.
4. **Surfaces** — `/lore`, an admin-menu section and button, and a daily timer that fires
   every `lore_interval_days`.

---

## 1. What exists

`store.messages` has held every message since 2026-08-18: 13,444 rows at the time of
writing, one chat (`-1004291515714`, «чат матсурі🎰»). `digest.py` turns each day into a
300-token summary and up to ten durable facts per day; 546 facts are stored. That is the
whole of the bot's memory.

Two things it does not hold:

* **Reactions.** `allowed_updates` is `["message", "edited_message", "callback_query"]`,
  so `message_reaction` never arrives. In the export, 4,115 of 43,147 messages carry at
  least one reaction. "The most-reacted message of the week" is unanswerable today.
* **Service events.** Joins, leaves, pins, title changes and the group→supergroup
  migration arrive as ordinary `Message` objects with no text, and `handlers.py` drops
  them. The export holds 61: twenty-one join requests, nineteen pins, twelve invites, one
  title change, one migration from «Дідові меми».

Both are lore material of the first order, and neither is recoverable later — Telegram
does not let a bot go back for them.

## 2. Why the daily summaries are not enough on their own

The obvious cheap build is to write the lore from `summaries` and `facts`: two days of
those is about 600 tokens. It was rejected. Those summaries are written to a prompt that
says *"це читатиме бот, щоб розуміти контекст, а не людина"* — deliberately dry,
quote-free, stripped of the wording that makes a joke a joke. Lore assembled from them
reads like meeting minutes.

The lore job therefore reads the raw transcript, and uses `facts` only as a cast list, so
the model does not have to rediscover who these people are on every run.

Cost is not the obstacle it looks like. Two days is roughly 6,600 messages and 200,000
characters, about 66,000 tokens by `context.estimate_tokens`. On `gemini-3.7-flash` a full
run — harvest plus rewrite, both with thinking enabled — costs an estimated **$0.25–0.35**,
or about **$4–5 a month** at a two-day cadence. Most of that is thinking tokens, which
bill at the output rate; see §5.4. The digest stays on `gemini-2.5-flash-lite` —
summarising does not need a better model, prose does.

## 3. Capture

### 3.1 Schema

Three tables added to `store.SCHEMA`, with matching `_migrate` entries so an existing
database picks them up on the next connect:

```sql
CREATE TABLE IF NOT EXISTS reactions (
    chat_id    INTEGER NOT NULL,
    message_id INTEGER NOT NULL,
    emoji      TEXT    NOT NULL,
    count      INTEGER NOT NULL,
    updated_at TEXT,
    PRIMARY KEY (chat_id, message_id, emoji)
);

CREATE TABLE IF NOT EXISTS events (
    chat_id    INTEGER NOT NULL,
    message_id INTEGER NOT NULL,
    ts         TEXT    NOT NULL,
    action     TEXT    NOT NULL,
    actor_id   INTEGER,
    payload    TEXT,
    PRIMARY KEY (chat_id, message_id)
);

CREATE TABLE IF NOT EXISTS lore (
    chat_id      INTEGER NOT NULL,
    version      INTEGER NOT NULL,
    text         TEXT    NOT NULL,
    created_at   TEXT    NOT NULL,
    model        TEXT,
    tokens       INTEGER,
    window_start TEXT,
    window_end   TEXT,
    PRIMARY KEY (chat_id, version)
);

CREATE INDEX IF NOT EXISTS idx_reactions_chat ON reactions (chat_id, count DESC);
CREATE INDEX IF NOT EXISTS idx_events_chat_ts ON events (chat_id, ts);
```

`payload` is JSON: the title for a rename, the member list for a join, the pinned message
id for a pin. Anything the renderer might want to say out loud, without a column per
action.

`lore` keeps every version rather than overwriting one row. A document the model is free
to amend is a document that can quietly lose a good line; keeping versions makes that
recoverable and costs a few kilobytes a week.

### 3.2 Reactions

`message_reaction` is added to `allowed_updates` in both `serve_webhook` and
`serve_polling`. `MessageReactionUpdated` carries the reacting user's `old_reaction` and
`new_reaction` lists, so the handler applies the difference to the stored counts: emojis
in `new` and not in `old` increment, the reverse decrement, rows reaching zero are
deleted.

Two constraints, both accepted deliberately:

* **The bot must be an administrator** in the chat to receive `message_reaction` at all.
  Гряг is one in «чат матсурі🎰». In a chat where it is not, reactions are simply absent
  and the lore is built without them — nothing else breaks.
* **Reaction counts drift low across downtime.** Telegram replays pending *messages* for
  24 hours but does not replay reaction updates, so anything reacted to while the bot is
  down is lost for good. The importer sets counts absolutely, live traffic only adjusts
  them. This is good enough for "which message made the chat laugh"; it is not good
  enough to build anything that must be exact, and nothing in this design does.

### 3.3 Service events

`handlers.py` stores service messages to `events` on the same path that stores text: the
`Message` fields `new_chat_members`, `left_chat_member`, `pinned_message`,
`new_chat_title`, `migrate_from_chat_id`, and the forum-topic ones. They do not enter
`messages`, so nothing about the conversation context or the reply gate changes.

## 4. Backfill

`python -m gryag.import_export chat_exports/ChatExport_2026-08-24/result.json`

A one-time script kept in the repo, because there will be another export.

The export runs 2026-08-11 → 2026-08-24: 43,147 messages, 38 people, and the week before
the bot was deployed. It is also a strictly richer record of the overlapping days than
what the bot captured live, since it carries reactions.

Mapping rules:

| Export | Stored |
| --- | --- |
| `id: 4291515714`, `type: private_supergroup` | `chat_id = -1004291515714` |
| `from_id: "user8792101665"` | `user_id = 8792101665` |
| `from_id: "channel…"` | skipped; channel posts have no user |
| `text_entities` | joined into plain text |
| `media_type` / `sticker_emoji` / `photo` | `media_kind` |
| `reply_to_message_id` | `reply_to` |
| `from` matching `гряг` or `context.OTHER_BOT_ALIASES` | `is_bot` / `sender_is_bot` |
| `reactions[].count` | `reactions` rows, set absolutely |
| `type: "service"` | `events` rows keyed by `action` |

Every insert is `ON CONFLICT DO NOTHING` on `(chat_id, message_id)`, so live rows always
win, and re-running the importer against a newer export is safe and idempotent. Users are
upserted with `store.upsert_user` so aliases come out of the same `context.alias_for` the
rest of the bot uses. The script reports inserted and skipped counts per table.

Edits are ignored: the export already holds the final text of the 6,476 edited messages.

## 5. The generator

`gryag/lore.py`, structured like `digest.py` and reusing its chunking, its refusal
handling and its usage accounting.

### 5.1 Window

From the previous version's `window_end` to now; from the oldest stored message if there
is no previous version. Capped at **four days** — a missed run must not silently produce a
130,000-token harvest, and four days of this chat is already more than the document can
absorb in one rewrite.

### 5.2 Stage one — harvest

The window is chunked at `CHUNK_TOKENS = 2000`, never breaking a message, exactly as the
digest does. Each chunk goes to the model on its own and comes back as JSON:

```json
{"beats": [{"who": ["…"], "what": "…", "quote": "…", "kind": "joke|drama|event|gag"}]}
```

Maximum eight beats per chunk. `quote` is optional and verbatim — it is the only channel
through which the chat's actual wording reaches the document.

Chunking is not a token economy here, it is blast-radius control. A single stretch of this
chat's real transcript has already come back `PROHIBITED_CONTENT` with no candidates, and
that filter is not configurable. One refused chunk must cost that chunk. Refusals are
counted and logged; a run where every chunk refuses fails loudly and leaves the previous
version standing.

### 5.3 The stats block

Computed in SQL, never asked of the model, which is bad at counting 3,300 messages and
good at being funny about a number handed to it:

* messages per person over the window, and the change against the previous window
* the three most-reacted messages, with their text and the reactions themselves
* busiest and deadest hour, longest silence
* joins, leaves, pins, title changes from `events`
* sticker champion, edit champion

### 5.4 Stage two — rewrite

One call. Input: the current document, every harvested beat, the stats block, and the
`facts` cast list for the people who appear. Output: the new document, Ukrainian,
Markdown, clamped with `context.clamp` to `lore_max_chars` (default 20,000).

The prompt tells the model it is maintaining one living page, not writing a new one: it
may amend a line, merge two, retire a joke that has died — and that dropping something
requires a reason, so the ceiling is met by compression rather than by truncation.

Voice comes from a short instruction inside the lore prompt, **not** from
`eval/persona-v3.txt`. That persona is tuned for one-line chat replies; pointed at a long
document it fights the format.

**Thinking is enabled on both stages** (`thinking_budget=-1`), unlike the digest, which
runs with it off. The harvest is a judgement call on every chunk — which of six thousand
lines are worth keeping — and the rewrite is the only genuinely creative call in the
project. Thinking tokens bill at the output rate and are the volatile part of a 3.x bill,
so this is the single largest cost lever in the design: it takes a run from roughly $0.10
to an estimated **$0.25–0.35**, about **$4–5 a month** at a two-day cadence. `lore_thinking`
is a menu knob (`авто` / `вимкнене`) so a run that turns out to think for a dollar can be
turned down without a deploy, and the `usage` table reports thought tokens separately.

Every call records to `usage` with `purpose="lore"`, so the existing spend panel shows it
beside `speak` and `digest` with no changes.

### 5.5 Failure

If stage two fails, refuses, or returns an empty body, the previous version stands and the
run logs an error. The document is never replaced by a partial one. A run triggered from
the menu reports the failure to the admin in the toast.

## 6. Surfaces

### 6.1 `/lore`

Registered with BotFather as `/lore`, and matched as plain text for `/лор` — Telegram only
registers ASCII commands, but nothing stops the bot answering the Cyrillic one people will
actually type.

It sends the latest stored version as `lore.md` (`BufferedInputFile`), captioned with the
version number and the date it was written. It is a database read and an upload; it never
calls the model, so it cannot be made expensive by being spammed.

Anyone in an enabled chat may use it. A `lore_cooldown` (default 600 s) per chat stops the
file-flood, persisted in `chat_state` rather than in memory, so a restart is not a fresh
spam window.

### 6.2 Admin menu

A new "Лор" section in `menu.SECTIONS`, which is all it takes for the settings to appear —
every entry names a config key and the callback plumbing is generic:

| Key | Default | Choices |
| --- | --- | --- |
| `lore_enabled` | `1` | так / ні |
| `lore_model` | `gemini-3.7-flash` | 3.7 flash / flash-latest / 2.5 lite |
| `lore_interval_days` | `2` | 1 / 2 / 7 |
| `lore_thinking` | `-1` (авто) | авто / вимкнене |
| `lore_max_chars` | `20000` | 10000 / 20000 / 40000 |

Plus a regenerate button, wired through an `on_lore` callback built in `__main__.build`,
following the `on_digest` pattern: one chat, the one whose button was tapped, spawned as a
background task so the callback can be answered immediately.

`lore_model` defaults to the pinned `gemini-3.7-flash`, not `gemini-flash-latest`.
`screens.drift_warning` exists because that alias is repointed with no notice and no API
signal; a document whose voice is quietly rewritten by a swapped model is precisely the
case nobody would catch until it had happened three times.

### 6.3 Schedule

`deploy/gryag-lore.service` and `gryag-lore.timer`, firing **daily at 05:00** — after the
04:00 digest, inside the same measured dead zone of 03:00–07:00.

The job itself decides whether to run: it exits without cost unless `lore_interval_days`
have passed since the latest version for that chat. Systemd's `OnCalendar` cannot express
"every second day" without breaking across month boundaries, and this way the cadence is a
menu knob instead of a unit-file edit.

## 7. Testing

* `tests/test_lore.py` — window selection including the four-day cap and the no-previous
  -version case; chunking; the stats SQL against a seeded database; the ceiling; and the
  refusal path leaving the previous version intact.
* `tests/test_import_export.py` — a trimmed fixture slice of the real export (a few dozen
  messages, one service event, one reaction), checking id mapping, idempotency on a second
  run, and that live rows survive an import.
* `tests/test_store.py` — reaction delta arithmetic, including a removal taking a count to
  zero, and event insertion.
* `tests/test_menu.py` — the new section renders and every key it names exists in
  `config.DEFAULTS`.

## 8. Decisions taken, and what they cost

**One living document, not a chronicle of dated chapters.** The document is rewritten each
run rather than appended to. It stays readable indefinitely and it stays current; the price
is that history is mutable, which is why every version is kept.

**Raw transcript, not the daily summaries.** Ten times the cost of the cheap build, and the
only version of it that is funny.

**Reactions accepted as approximate.** See §3.2. The alternative is polling the API for
reaction counts, which the Bot API does not offer.

**Reading is free, writing is gated.** `/lore` is open to the chat because the document is
the chat's own; regeneration is the timer and the admin, because that is what spends money
and what can degrade the document.
